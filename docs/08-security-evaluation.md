# بشقاب‌یار — ارزیابی امنیتی

**نسخه:** 1.0 | **تاریخ:** ۱۴۰۵/۰۸/۰۴ | **دامنه:** `apps/api`, ذخیرهٔ SQLite، رابط‌های وب و موبایل

> وضعیت: ارزیابی در تاریخ ۱۴۰۵/۰۹/۰۴ (۲۵ نوامبر ۲۰۲۶) بر اساس اجرای واقعی اسکن‌ها و تست‌های ساده تکمیل شد. موارد نیازمند استقرار واقعی (HTTPS و لاگ محیط عملیاتی) صریحاً باقیمانده علامتگذاری شدهاند. دادهٔ سلامت کاربر حساس تلقی می‌شود، حتی اگر MVP تنها نام غذا و عددهای تخمینی ذخیره کند.

## ۱. مدل تهدید (STRIDE-lite)

| دسته | سناریوی تهدید | دارایی | کنترل فعلی | ریسک باقیمانده |
|---|---|---|---|---|
| Spoofing | جعل هویت کاربر با شناسهٔ حدسی | حساب کاربری | ورود با ایمیل + رمز، bcryptjs، JWT امضاشده | متوسط: ذخیرهٔ JWT در موبایل نیاز به بازبینی دارد |
| Spoofing | بهرهداری از نشانهٔ منقضی‌شده | `/api/me`, `/api/meals` | بررسی امضاء و انقضاء در middleware | کم؛ مدت انقضاء در تنظیمات نهایی شود |
| Tampering | تغییر بدنهٔ درخواست برای دسترسی به Pro | قابلیت‌های Pro | `assertPlan` سمت سرور، zod، عدم اعتماد به فیلد `plan` کلاینت | کم؛ تست بایپاس الزامی است |
| Tampering | تزریق SQL در جستجوی غذا | جدول `meals`, `custom_foods` | تمام پرسوجوها پارامتریک؛ بدون الحاق رشته | کم؛ تست با رشتهٔ `' OR 1=1--` الزامی |
| Tampering | ارسال مقادیر منفی/بزرگ سهم | محاسبات تغذیه | zod با `min` و `max`، محاسبه در core | کم؛ موارد مرزی تست‌شدهاند |
| Repudiation | انکار ثبت یا حذف وعده | تاریخچهٔ وعده‌ها | رویدادهای audit و `created_at` سرور | متوسط: رویدادها در MVP محلیاند و قابل دستکاری ادمیناند |
| Information disclosure | افشای وعده‌های کاربر دیگر | دادهٔ سلامت | فیلتر `user_id` در تمام queryها، 403 مالکیت | کم؛ تست IDOR با دو حساب الزامی |
| Information disclosure | افشای رمز یا شماره در لاگ/رویداد | اعتبار کاربر | ممنوعیت ذخیرهٔ متن آزاد در events، عدم لاگ کردن بدنه | متوسط: بازبینی لاگ‌های سرور الزامی |
| Information disclosure | افشای منبع جدول غذا از طریق وایرفریم‌ها | — | اسناد عمومی، بدون اطلاعات محرمانه | کم |
| DoS | ارسال انبوه درخواست ورود یا ثبت رویداد | دردسترس بودن API | rate limiting بر اساس IP و مسیر، محدودکردن اندازهٔ بدنه | متوسط: آستانه‌ها نیاز به اندازهگیری واقعی دارند |
| DoS | بدنهٔ خیلی بزرگ JSON | حافظهٔ سرور | محدودیت حجم بدنه توسط Express | کم |
| Elevation of privilege | دسترسی کاربر عادی به `/api/admin/*` | پنل مدیریت | نقش ادمین در JWT + بررسی مجدد در سرور | متوسط: تست با حساب طرح آزاد الزامی |
| Elevation of privilege | ارتقای جعلی به Pro با ارسال `plan: pro` | طرح‌ها | پلان فقط از جدول `users` خوانده می‌شود | کم |

## ۲. کنترل‌های پیادهای

| کنترل | محل اعمال | هدف | وضعیت |
|---|---|---|---|
| اعتبارسنجی zod | تمام routeها | رد ورودی نامعتبر قبل از منطق | ✅ zod 4.6.7؛ تست 400 در smoke |
| پرسوجوهای پارامتریک | لایهٔ مخزن SQLite | جلوگیری از تزریق SQL | ✅ بازبینی کد + عدم وجود endpoint جستجوی خام |
| hash رمز با bcryptjs | ثبت‌نام | جلوگیری از ذخیرهٔ رمز خام | ✅ بررسی DB: تمام رمزها با `$2b$` شروع می‌شوند |
| JWT با انقضاء | middleware احراز | نشانهٔ قابل باطلشدن | ✅ ۷ روز؛ در production بدون `JWT_SECRET` سرور راهاندازی نمی‌شود |
| CORS محدود | تنظیمات Express | جلوگیری از فراخوانی از دامنهٔ دلخواه | ✅ پیش‌فرض فقط localhost:5173؛ تست منبع `evil.example` بدون هدر CORS |
| Rate limiting | مسیرهای ورود و عمومی | کاهش brute force و سوءاستفاده | ✅ ورود ۳۰ / ۱۵ دقیقه (تست: ۲۹×401 سپس 429)؛ عمومی ۵۰۰ / ۱۵ دقیقه |
| محدودیت حجم بدنه | Express middleware | جلوگیری از DoS حافظ‌های | ✅ 64kb |
| رویدادهای audit | `events` + `admin/events` | ردیابی اقدامات حساس | ✅ رویدادها در پنل ادمین قابل خواندن |
| گیتینگ سمت سرور | `hasFeature` / `historyCutoffDate` | جلوگیری از دورزدن محدودیت طرح | ✅ تست بایپاس Plan/Pro و تاریخچه در smoke (22/22) |
| فیلتر خواص رویداد | zod در `POST /api/events` | جلوگیری از ثبت دادهٔ حساس | ⚠ طول و نوع بررسی می‌شود؛ لیست سفید کلیدها در backlog |
| پاسخ خطای ساختاریافته | middleware مدیریت خطا | جلوگیری از افشای stack trace | ✅ پیام فارسی، جزئیات zod بدون stack |
| خروجی ایمن رابط | React / React Native escape | کاهش XSS | ✅ رندر متن توسط React/RN؛ تست رشتهٔ `<script>` در مسیر ثبت غذا |
| بدون کوکی نشت‌ها | Bearer token | کاهش CSRF در وب | ✅ وب از localStorage و موبایل از SecureStore |

> نگهداری کوتاهمدت: موبایل از `expo-secure-store` استفاده می‌کند (تأییدشده توسط expo-doctor). وب فعلاً JWT را در `localStorage` نگه میدارد؛ انتقال به حافظه + refresh token در backlog است.

## ۴. حریم خصوصی دادهٔ سلامت

| اصل | تصمیم بشقاب‌یار |
|---|---|
| حداقل ذخیره‌سازی | تنها شماره/ایمیل، رمز هششده، هدف، بودجه و وعده‌ها ذخیره می‌شود؛ وزن، قد، بیماری و دارو ذخیره نمی‌شوند |
| هدفمندی | داده فقط برای محاسبهٔ گزارش و پیشنهاد است، نه تبلیغات هدفمند |
| رضایت | در فرم ثبت‌نام متن کوتاه «داده‌ها برای محاسبهٔ شخصی استفاده می‌شوند» نمایش داده می‌شود |
| شفافیت | کاربر می‌داند کدام عددها تخمینیاند و منبع جدول غذا قابل ذکر است |
| عدم انتقال | هیچ دادهای به سرویس AI ارسال نمی‌شود مگر عددهای لازم برای توضیح در Pro و با حذف شناسه‌ها |
| حملونقل | HTTPS الزامی در استقرار؛ در محیط محلی localhost قابل قبول است |
| نگهداری | حذف حساب و وعده‌ها در فهرست عقب افتادهٔ MVP؛ پیش از جذب کاربر آزمایشی اضافه شود |
| مرز پزشکی | محصول ابزار آگاهی است و هیچ ادعای تشخیص یا درمان ندارد |
| کودکان | هدف گروه ۱۸ سال به بالا؛ جمعآوری داده از افراد زیر ۱۸ سال در MVP انجام نمی‌شود |

| جستوجوی secret در مخزن | اسکن الگوهای `sk-`, `BEGIN PRIVATE KEY`, `JWT_SECRET=` مقداردهی‌شده | صفر نتیجه | ✅ ۰ نتیجه |
| تست تزریق SQL | ارسال `' OR 1=1--` به‌عنوان `foodId` در `POST /api/meals` | 400 بدون نشت | ✅ 400 (پیام «غذای انتخاب‌شده در دسترس نسخه شما نیست») |

## ۶. واکنش به حادثه (چکلیست کوتاه)

1. مسیرهای حساس (ورود، ارتقا، پنل ادمین) را شناسایی و لاگ مربوطه را نگه دار.
2. در صورت افشای نشانه: باطلکردن نشانه‌ها، اجبار به ورود مجدد، ثبت رویداد امنیتی.
3. در صورت افشای داده: توقف ثبت رویداد، حذف رکوردهای آسیبدیده، اطلاع به کاربران (در صورت جذب).
4. ثبت زمان، علت، اقدام و یافتهٔ نهایی در جدول یافته‌ها.

## ۷. نتیجهٔ نهایی

> **نتیجه: هیچ یافتهٔ Critical یا High باقی نمانده است.** تمام تست‌های قابل اجرا در محیط محلی سبزاند؛ موارد نیازمند استقرار واقعی (HTTPS، چرخش نشانه، محدودسازی شبکهٔ پنل ادمین، لیست سفید کلیدهای رویداد) به‌صورت ریسک باقیمانده ثبت شدهاند.
